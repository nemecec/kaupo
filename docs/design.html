1.The name

Kaupo — an Estonian male given name (Kaupo of Turaida) derived from kaup, "goods / wares / merchandise". Short, pronounceable, and literally about trading. The public platform repo is kaupo; the private strategies repo is kaupo-strategies.

Alternatives if you don't like it: Kasum — "profit"; Turg — "market".

2.What we're building

A self-hosted, open-source platform that:

  • runs 24/7 in the background and trades fully autonomously — you review dashboards and reports, you never click "buy";
  • treats strategies as deterministic code plugins, developed together with AI agents in a separate, private repo;
  • gives agents fast feedback loops: the same strategy code runs unchanged in backtest, shadow (paper), and live modes;
  • supports scheduled strategy review (e.g. every 24 h) driven by AI agents through machine-readable APIs and reports;
  • starts simple (one exchange, candles, no sentiment) and grows (sentiment, multi-exchange, portfolio risk).

Design principles

  1. One strategy code, three execution modes. Backtest, shadow, and live share the exact same engine loop; only the candle source and the venue adapter differ. This is what makes backtests trustworthy and gives agents a reliable feedback signal.
  2. Determinism by contract. Strategies never see wall-clock time, never do I/O, never get unseeded randomness. All inputs come through a context object. Enforced by SDK design + lint + tests.
  3. Agent-first interfaces. Everything the system does is reachable via documented REST/OpenAPI + CLI + JSON artifacts — an AI agent can pull reports, run backtests, and compare runs without a human.
  4. Cost-conscious. Single small server, co-located Postgres, no Kubernetes, no managed services until they're clearly needed. Target ~$15–20/mo (less on free tier).
  5. Risk manager is not a strategy. Hard guardrails (position limits, daily-loss halt, pair whitelist, no leverage, kill switch) live outside strategy code and apply to live and shadow.

5.Strategy SDK — the contract agents code against

class Strategy(Protocol):
    id: str                           # "regime-switch-btc-eur"
    params_schema: type[BaseModel]    # pydantic — params validated at load

    def on_candle(self, ctx: Context) -> list[OrderIntent]: ...

class Context(Protocol):
    clock: Clock                  # virtual in backtest, real in live — only time source
    candle: Candle                # just-closed candle
    history(pair, timeframe, n)   # lookback window, read-only
    position(pair)                # current position for this run
    equity() -> Decimal
    # indicator helpers: ADX, Bollinger, ATR, RSI…

class OrderIntent:  # what the strategy wants; risk manager decides what it gets
    side, size, order_type, limit_price, stop_loss, take_profit, reason

Rules enforced: no datetime.now(), no network/file I/O, no mutable globals (state lives in declared fields so backtests can snapshot/reset). A make lint-strategy check plus SDK design make violations hard. Open-source example strategies (regime detection via ADX + Bollinger width, switching between mean-reversion and momentum modules — from our earlier discussion) ship in examples/strategies/ as reference implementations.

6.Execution modes

Candle sourcehistorical (DB)live WebSocketlive WebSocket
Venuepaper (fees + slippage modeled)paper (same model)Kraken via ccxt
Moneyvirtual ledgervirtual ledgerreal ledger
Purposeagent feedback loopforward validationreal trading
  • Backtester: event-driven, identical loop to live. Inputs: strategy ref, params, pairs, date range, fee/slippage model. Each run stores equity curve, trades, and metrics (total return, CAGR, Sharpe, Sortino, max drawdown, win rate, avg win/loss, exposure %, fees paid, regime stats). Runnable via CLI (no services needed) or API (async job). Months of 1h candles run in seconds → agents get near-immediate feedback.
  • Shadow: N concurrent shadow runs supported (strategy v1 vs v2 A/B on live data, virtual money).
  • Live: phase 3, only after a shadow track record. The real venue adapter adds order reconciliation (exchange state vs ledger) and crash recovery.

Risk manager (all modes): max position per pair, max gross exposure, max daily loss → auto-halt, pair whitelist, no leverage, min notional, cooldown after N consecutive losses. Configured per run; cannot be weakened by strategy params.

7.AI-agent integration & review cadence

Agents get no special backdoor — they use the same public interfaces:

  • OpenAPI-documented REST (/api/v1/…) + CLI (kaupo backtest …, kaupo report …) + JSON artifacts.
  • GET /api/v1/reports/daily?date=… — machine-readable JSON: per-run equity, P&L attribution, trades, drawdowns, anomalies, data gaps.
  • POST /api/v1/backtests (async) → poll GET /api/v1/backtests/{id} for metrics.

Review cadence (configurable, default daily)

Implemented as a GitHub Actions schedule: workflow in kaupo-strategies (cron, e.g. 06:00 UTC). The job runs an AI agent headless, which:

  1. pulls daily reports from the API (read-only token);
  2. forms hypotheses → runs backtests (in CI against a synced candle dump — free compute — or via API);
  3. proposes changes → opens a PR in kaupo-strategies.

Promotion pipeline (phase 3)

Merged PR → engine reloads strategies → new version automatically starts shadowing → if it passes the gates in promotion.yml (min shadow duration, Sharpe ≥ X, max drawdown ≤ Y), it's flagged for promotion → you approve with one click (full auto later if you want).

Why GitHub-native instead of an in-system scheduler: strategy iteration already lives in that repo, Actions provides free backtest compute, PRs give an audit trail of every agent decision, and the engine stays simpler. (If you later prefer in-system triggering, the engine can emit a webhook on a cron — the API surface doesn't change.)

8.Data model (PostgreSQL)

Plain Postgres 16 with good indexes — sufficient for a handful of pairs × 1m/1h candles (millions of rows is trivial). TimescaleDB extension as a later option, not a dependency.

  • candles(pair, timeframe, ts, open, high, low, close, volume) — unique (pair, timeframe, ts)
  • strategies(id, version, source_hash, params jsonb)
  • runs(id, mode, strategy_id, started_at, ended_at, status, config jsonb, metrics jsonb)
  • orders(id, run_id, ts, pair, side, type, size, limit_price, status, filled_price, fee)
  • fills(id, order_id, ts, price, size, fee)
  • ledger_entries(run_id, ts, asset, amount, balance_after, reason, ref_id) — append-only
  • equity_snapshots(run_id, ts, equity, cash, unrealized_pnl)
  • reports(id, ts, period, run_id, body jsonb)
  • events(id, ts, level, source, message, data jsonb) — alerts / audit log

Backups: nightly pg_dump → S3 with lifecycle expiry (pennies/month).

9.API surface (FastAPI)

  • GET /health, GET /api/v1/status — engine status, active runs, mode
  • GET /api/v1/candles?pair=&timeframe=&from=&to=
  • POST /api/v1/backtests / GET /api/v1/backtests/{id} (+ equity curve, trades)
  • GET /api/v1/runs?mode=…, GET /api/v1/runs/{id}/equity|orders|trades|positions
  • GET /api/v1/reports/daily?date=…
  • POST /api/v1/control/pause | resume | kill — kill switch (authenticated)
  • WS /ws/live — live ticks, equity updates, fill events for the dashboard

Auth: single user → one admin token + one read-only token (the latter is what agents get). No user management. OpenAPI schema → generated TypeScript client for the UI.

10.UI (React + TypeScript)

React 19 + TypeScript + Vite + TanStack Query + TradingView lightweight-charts (OSS, purpose-built for candles/equity curves) + Tailwind. Typed API client generated from OpenAPI — end-to-end type safety.

  • Dashboard — total equity curve, P&L day/week/month, open positions, engine status, kill switch
  • Runs — list/filter backtest & shadow runs, compare two runs
  • Run detail — equity + drawdown charts, trades overlaid on candle chart, metrics table, params
  • Trades/Orders — filterable tables
  • Reports — daily report viewer
  • Alerts/Events — audit log

Alternatives considered: Svelte/Solid — nicer DX but thinner financial-charting ecosystem; Next.js — unnecessary for a single-user dashboard. React + Vite SPA is the pragmatic choice.

11.Testing strategy

  • Unit (pytest): indicators (validated against ta reference values), ledger math, risk rules, regime detector, metrics calculations.
  • Behaviour (pytest scenario tests): canned candle sequences → expected order traces, run identically through all three modes to prove backtest/shadow/live parity; kill-switch and daily-loss-halt scenarios; golden-file metrics.
  • Integration: testcontainers Postgres (migrations + repositories), fake venue with recorded fixtures (no network in CI), API contract tests (httpx), end-to-end backtest via CLI.
  • UI: Vitest + React Testing Library; Playwright smoke test against the compose stack.
  • CI (GitHub Actions): ruff, mypy, pytest with coverage gate, UI tests, docker build. Same shape in kaupo-strategies so every agent PR is tested before merge.

12.Deployment & costs

Local: docker compose up → Postgres + engine + UI. Backtests additionally runnable service-free via CLI against a local candle cache.

AWS (cost-conscious target ~$15–20/mo):

  • One EC2 t4g.small (ARM, 2 GB, ~$12/mo) running the same docker compose stack (engine + Postgres + UI behind Caddy with auto-TLS). AWS free tier can cover most of year one.
  • 20 GB gp3 EBS (~$1.6/mo); nightly pg_dump → S3, lifecycle-expired after 30 days (pennies).
  • Secrets in SSM Parameter Store (free); GitHub Actions deploys via OIDC + SSM Run Command — no SSH port open, no stored AWS keys.
  • Optional: expose UI only over Tailscale (free) instead of public HTTPS.
  • Documented scaling path (when justified, not before): RDS Postgres + ECS Fargate, ~$50–70/mo.

13.Phased roadmap

Phase 1 — MVP implementation scope of this plan

  1. Repo scaffold: monorepo, CI, ruff/mypy, docker-compose, Postgres + migrations
  2. Candle ingestion: Kraken historical backfill (REST) + live (WS), storage layer
  3. Strategy SDK + protocol + lint rules
  4. Backtesting engine + paper venue (fees/slippage) + metrics
  5. Ledger/portfolio accounting
  6. CLI (kaupo ingest, kaupo backtest, kaupo run shadow)
  7. Shadow trading mode on live data
  8. FastAPI: status, runs, backtests, equity/trades, WebSocket
  9. UI: dashboard, runs list/compare, run detail with charts, trades
  10. Example open-source strategy: regime-switch (ADX/Bollinger) mean-reversion ↔ momentum
  11. Tests across all levels; coverage gate green
  12. Daily report endpoint (JSON)

Phase 2 — AWS & agents

EC2 deploy via Actions/SSM, auth tokens, S3 backups, Telegram alerts, kaupo-strategies repo + scheduled agent review workflow.

Phase 3 — Live trading

Kraken venue hardening, reconciliation, kill switch, promotion gates, tiny capital start.

Phase 4+

Sentiment module, multi-exchange, parameter sweeps/optimization, portfolio-level risk, TimescaleDB if needed.

14.Tech stack summary

Python 3.12 (engine/api/cli — ccxt, pandas, pydantic, FastAPI, pytest), PostgreSQL 16, Docker Compose, React 19 + TypeScript + Vite + lightweight-charts, GitHub Actions CI/CD, AWS (EC2 + S3 + SSM).

Python over Kotlin, confirmed: the trading/backtesting/data ecosystem (ccxt, pandas, ta) is where agents and strategy code will live; the JVM would only add friction.
