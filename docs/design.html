1.The name

Kaupo is an Estonian male given name (Kaupo of Turaida). It comes from kaup, which means "goods" or "merchandise". It is short and easy to pronounce. The public platform repository is kaupo. The private strategies repository is kaupo-strategies.

Alternatives: Kasum ("profit") or Turg ("market").

2.What we are building

A self-hosted, open-source platform with these properties:

  • It runs in the background and trades without manual input. The user reviews dashboards and reports. The user never clicks "buy".
  • Strategies are deterministic code plugins. The user develops them with AI agents in a separate private repository.
  • The same strategy code runs in backtest, shadow, and live modes. This gives agents a fast feedback loop.
  • AI agents review the strategies on a schedule (for example every 24 hours). They use machine-readable APIs and reports.
  • The system starts simple: one exchange, candles, no sentiment analysis. It grows later.

Design principles

  1. One strategy code, three execution modes. Backtest, shadow, and live share the same engine loop. Only the candle source and the venue differ. This makes backtests trustworthy. It gives agents a reliable feedback signal.
  2. Determinism by contract. Strategies never see wall-clock time. They do no I/O. They get no unseeded randomness. All inputs come through a context object. The SDK design, the linter, and the tests enforce this.
  3. Agent-first interfaces. Every function is reachable through a documented REST API, the CLI, and JSON artifacts. An AI agent can pull reports, run backtests, and compare runs without a human.
  4. Cost-conscious. One small server, co-located Postgres, no Kubernetes, no managed services. Target cost: under 10 EUR per month.
  5. The risk manager is not a strategy. Hard guardrails live outside the strategy code. Position limits, daily-loss halt, pair whitelist, no leverage, and a kill switch. They apply to live and shadow trading.

The system is a single deployable unit: a modular monolith. Locally it runs as three containers: postgres, engine (core plus API), and ui (static files behind nginx). Strategies are volume-mounted. They are not baked into the image.

5.Strategy SDK — the contract agents code against

class Strategy(Protocol):
    id: str                           # "regime-switch-btc-eur"
    params_schema: type[BaseModel]    # pydantic — params validated at load

    def on_candle(self, ctx: Context) -> list[OrderIntent]: ...

class Context(Protocol):
    clock: Clock                  # virtual in backtest, real in live — only time source
    candle: Candle                # just-closed candle
    history(pair, timeframe, n)   # lookback window, read-only
    position(pair)                # current position for this run
    equity() -> Decimal
    # indicator helpers: ADX, Bollinger, ATR, RSI…

class OrderIntent:  # what the strategy wants; risk manager decides what it gets
    side, size, order_type, limit_price, stop_loss, take_profit, reason

The rules are: no datetime.now(), no network or file I/O, no unseeded randomness. The CLI, the API, and CI enforce them with kaupo lint-strategies. The linter is a tripwire for plausible mistakes, not a security boundary. The repository ships open-source example strategies in examples/strategies/. One of them detects the market regime with ADX and Bollinger width. It switches between a mean-reversion module and a momentum module.

6.Execution modes

Moneyvirtual ledgervirtual ledgerreal ledger
Purposeagent feedback loopforward validationreal trading
  • Backtester: event-driven, with the same loop as live trading. Inputs: strategy, parameters, pair, date range, and the fee model. Each run stores the equity curve, the trades, and the metrics. The metrics include total return, Sharpe ratio, max drawdown, win rate, and fees paid. You can run it through the CLI or the API. Months of 1h candles run in seconds. Agents get almost immediate feedback.
  • Shadow: several shadow runs can run at the same time. For example, strategy v1 against v2 on live data with virtual money.
  • Live: Phase 3, only after a shadow track record exists. The real venue adapter adds order reconciliation and crash recovery.

Risk manager (all modes): max position per pair, max gross exposure, max daily loss (which halts the run), pair whitelist, no leverage, minimum order size, and a cooldown after consecutive losses. The configuration is per run. Strategy parameters cannot weaken it.

7.AI-agent integration and review cadence

Agents get no special backdoor. They use the same public interfaces:

  • OpenAPI-documented REST (/api/v1/…), the CLI (kaupo backtest …), and JSON artifacts.
  • GET /api/v1/reports/daily?date=… returns machine-readable JSON: per-run equity, P&L, trades, drawdowns, anomalies, and data gaps.
  • POST /api/v1/backtests starts an async job. Poll GET /api/v1/backtests/{id} for the metrics.

Review cadence (configurable, daily by default)

A GitHub Actions schedule: workflow in kaupo-strategies runs the review (for example at 06:13 UTC). The job runs an AI agent without a human in the loop. The agent does these steps:

  1. It pulls the daily reports from the API with the read-only token.
  2. It forms hypotheses and runs backtests through the API.
  3. It proposes changes and opens a pull request in kaupo-strategies.

Promotion pipeline (phase 3)

A merged pull request makes the engine load the new strategy version. The new version starts shadowing automatically. If it passes the gates in promotion.yml (minimum shadow duration, Sharpe ratio, max drawdown), the system flags it for promotion. You approve the promotion to live trading with one click.

Why GitHub-native and not an in-system scheduler: the strategy iteration already lives in that repository. Actions gives free compute for backtests. Pull requests give an audit trail of every agent decision. The engine stays simpler.

8.Data model (PostgreSQL)

Plain Postgres 16 with good indexes is sufficient. A handful of pairs at 1m or 1h candles means millions of rows, which is trivial for Postgres. TimescaleDB is a later option, not a dependency.

  • candles(pair, timeframe, ts, open, high, low, close, volume) — unique (pair, timeframe, ts)
  • strategies(id, version, source_hash, params jsonb)
  • runs(id, mode, strategy_id, started_at, ended_at, status, config jsonb, metrics jsonb)
  • orders(id, run_id, ts, pair, side, type, size, limit_price, status, filled_price, fee)
  • fills(id, order_id, ts, price, size, fee)
  • ledger_entries(run_id, ts, asset, amount, balance_after, reason, ref_id) — append-only
  • equity_snapshots(run_id, ts, equity, cash, unrealized_pnl)
  • reports(id, ts, period, run_id, body jsonb)
  • events(id, ts, level, source, message, data jsonb) — alerts and audit log

Backups: a nightly pg_dump goes to S3 with lifecycle expiry. This costs pennies per month.

9.API surface (FastAPI)

  • GET /health, GET /api/v1/status — engine status, active runs, mode
  • GET /api/v1/candles?pair=&timeframe=&start=&end=
  • POST /api/v1/backtests / GET /api/v1/backtests/{id} (+ equity curve, trades)
  • GET /api/v1/runs?mode=…, GET /api/v1/runs/{id}/equity|orders|trades|positions
  • GET /api/v1/reports/daily?date=…
  • POST /api/v1/control/pause | resume | kill — kill switch (authenticated)
  • WS /ws/live — live status updates for the dashboard (token in the query string)

Auth uses two bearer tokens. The admin token gives full access. The read-only token is for agents. There is no user management. The OpenAPI schema generates the TypeScript client for the UI.

10.UI (React + TypeScript)

The dashboard uses React 19, TypeScript, Vite, TanStack Query, TradingView lightweight-charts, and Tailwind. The charts library is open-source and purpose-built for candles and equity curves.

  • Dashboard — equity curve, P&L, open positions, engine status, kill switch
  • Runs — list and filter runs, open a run detail
  • Run detail — equity and drawdown charts, trades on the candle chart, metrics, parameters
  • Trades/Orders — filterable tables
  • Reports — the daily report viewer
  • Events — the audit log

Alternatives considered: Svelte and Solid have a nicer developer experience but a thinner charting ecosystem. Next.js is unnecessary for a single-user dashboard. React plus Vite is the pragmatic choice.

11.Testing strategy

  • Unit (pytest): indicators (validated against pandas references), ledger math, risk rules, and metrics.
  • Behaviour (pytest scenario tests): canned candle sequences produce expected order traces. The same scenario runs in backtest and shadow mode to prove parity. Golden-file metrics pin exact numbers.
  • Integration: testcontainers Postgres for migrations and repositories, scripted fake exchanges (no network in CI), API contract tests, and a full backtest-to-database path.
  • UI: Vitest and React Testing Library.
  • CI (GitHub Actions): ruff, mypy, pytest with a coverage gate, UI tests, and a Docker build with a smoke test. The kaupo-strategies CI has the same shape. Every agent pull request is tested before merge.

12.Deployment and costs

Local: docker compose up starts Postgres, the engine, and the UI. You can also run backtests without services through the CLI.

Production (target: under 10 EUR per month):

  • One Hetzner CX23 server (x86, 2 vCPU, 4 GB, about 6 EUR per month with IPv4). It runs the same docker compose stack behind Caddy at kaupo.trade, with automatic HTTPS certificates.
  • Durability: Hetzner keeps seven daily whole-disk backups for 20 percent of the server price. A nightly pg_dump also goes to AWS S3 and expires after 30 days. This is the cross-provider copy.
  • Images live in GHCR. GitHub Actions deploys over SSH after a green CI run. Inbound ports are 22, 80, and 443 only. Secrets travel as GitHub secrets and land on the host with mode 600.
  • A documented scaling path exists for later: ECS Fargate plus RDS on AWS, at 50–70 USD per month. The containers and images move as they are.

13.Phased roadmap

Phase 1 — MVP implementation scope of this plan

  1. Repository scaffold: monorepo, CI, ruff/mypy, docker-compose, Postgres plus migrations
  2. Candle ingestion: Kraken historical backfill and live polling
  3. Strategy SDK, protocol, and lint rules
  4. Backtesting engine, paper venue (fees and slippage), and metrics
  5. Ledger and portfolio accounting
  6. CLI (kaupo ingest, kaupo backtest, kaupo run shadow)
  7. Shadow trading mode on live data
  8. FastAPI: status, runs, backtests, equity/trades, WebSocket
  9. UI: dashboard, runs list, run detail with charts, trades
  10. Example open-source strategy: regime-switch (mean-reversion and momentum)
  11. Tests across all levels with a green coverage gate
  12. Daily report endpoint (JSON)

Phase 2 — Production and agents

Hetzner deployment through GitHub Actions and SSH, GHCR images, S3 backups, Telegram alerts, and the scheduled agent review workflow in kaupo-strategies.

Phase 3 — Live trading

Kraken venue hardening, reconciliation, promotion gates, position recovery on restart, and a small amount of starting capital.

Phase 4+

Sentiment module, multi-exchange support, parameter optimization, and portfolio-level risk.

Known gaps (tracked)

  • Position recovery on restart: a restarted run starts with a fresh ledger. A position that was open at shutdown is forgotten. This is acceptable for backtests but wrong for long-running daemons. The Phase 3 fix rebuilds the ledger from the entries of the previous run.
  • PYTHONHASHSEED nondeterminism: hash(str) and set iteration order vary per process. Strategies that rely on them break cross-process parity. This is a documented lint limitation.
  • Live venue: partial fills need strategy-side reconciliation. The SDK has no fill callback yet.

14.Tech stack summary

Python 3.12 (engine, API, CLI), PostgreSQL 16, Docker Compose, React 19 plus TypeScript and Vite, lightweight-charts, GitHub Actions CI/CD, and Hetzner Cloud (CX23, Caddy, GHCR) with AWS S3 for backups.

Python over Kotlin, confirmed. The trading and data ecosystem (ccxt, pandas, ta) is where agents and strategy code live. The JVM only adds friction here.
